# Roll patchright-core, track microsoft/playwright-cli

Two upstreams feed this repository. Both are kept as a separate layer under the code, so an update is a merge, not a re-port (`scripts/upstream/lib.ts` is the model):

- `patchright-core` (npm). The daemon runs untouched from `node_modules`; `src/*.ts` were forked from its compiled client. The package carries no TypeScript, so the pristine sources are the Playwright files at the tag whose compiled client is byte-identical to the package (`matchPlaywrightVersion` finds that tag by comparing the compiled files). `vendor/cli-client/` holds those pristine files; `src/` is our layer on top.
- `microsoft/playwright-cli` (git), the repository this fork descends from. `vendor/playwright-cli/` holds the pristine copy of the one file we still carry modified (`tests/integration.spec.ts` -> `tests/integration/core.spec.ts`); the files we rewrote (README, dev skill, shim, workflows) are only reported.

`scripts/upstream-snapshot/versions.json` records what the checkout is based on (patchright-core version, the matched Playwright tag, the tracked playwright-cli commit, hashes of every vendored file). `client.patch` next to it is our layer as a readable diff, regenerated by `npm run upstream:patch`; it documents, it is never applied. `vendor/` is never edited by hand: `npm run check` fails when a vendored file no longer matches its recorded hash.

`patchright-core` is pinned exactly: patchright has no `next` dist-tag, lags Playwright minors by weeks, and its patcher regularly breaks for 1–4 days after a Playwright release. Do not roll to a version younger than 48 hours (`--check` enforces it; `--force` overrides).

## What a roll does

`npm run roll -- <version>` (or `latest`):

1. downloads the current and the target `patchright-core`, diffs the compiled files we fork from, the command list, the daemon flags and the `PWTEST_*` hooks;
2. finds the Playwright tag with the byte-identical compiled client and fetches the pristine TypeScript of every forked file at that tag;
3. three-way merges each forked file with `git merge-file`: `src` (ours) <- `vendor` (base) -> upstream (theirs). Upstream-only changes land, our changes survive, an overlap is a conflict;
4. classifies: `safe` (nothing we fork from changed: only the daemon and the patches moved), `review` (merged cleanly but the client surface moved: new commands, daemon flags, upstream files, skill), `blocked` (a conflict, no merge base, or a missing hook);
5. unless `--dry-run` or blocked: writes `src/` and `vendor/`, bumps both pins, `npm install`, regenerates `src/help/help.generated.json`, refreshes `scripts/upstream-snapshot/` (compiled snapshot, `versions.json`, `client.patch`).

Nothing is written when blocked: the merges with conflict markers go to `.roll/conflicts/<file>.merged`, the report to `.roll/report.md`, the verdict to `.roll/result.json` (exit code 2). `--dry-run` produces the same report and changes nothing (exit 0).

## Steps by hand

1. `npm run upstream:check` — is there a newer release, how old is it.
2. `git checkout -b roll_<version>`.
3. `npm run roll -- <version> --dry-run`, read `.roll/report.md`.
4. `npm run roll -- <version>`.
5. If blocked: open `.roll/conflicts/<file>.merged`, resolve the hunks into `src/<file>` (ours = `src`, base = `vendor`, the `upstream` side is the new code), then run step 4 again: a file that already contains the upstream change merges cleanly.
6. New commands: decide on a guard in `src/stealth/guards.ts` and document them in `skills/patchright-cli/SKILL.md`; the help overlay test forces the decision. New daemon flags: `Session.daemonArgs` and the launch profile.
7. What patchright itself changed between the two versions goes into the residual-leak list in `skills/patchright-cli/references/stealth.md` when a leak was closed or opened:
   ```bash
   git fetch patchright && git log --oneline patchright/v<old>..patchright/v<new>
   ```
8. `npm run check && npm test` locally first (the stealth project needs a display), then CI.
9. `node bin/patchright-cli.js selftest` — paste the summary line into the PR.
10. An `Upstream:` line under Unreleased in `CHANGELOG.md`; commit `chore: roll patchright-core to <version>`.

`npm run upstream:verify` re-checks, with network, that `vendor/` equals the recorded Playwright tag and that the installed compiled client equals `playwright-core` at that version.

## Automation

- `.github/workflows/upstream-roll.yml` runs daily: detects a newer, old-enough `patchright-core`, rolls it on `roll_<version>`, runs the full CI matrix on that branch (the reusable `ci.yml`), and opens the PR with the report. `safe` + green CI is merged automatically; `review` waits for a human (label `needs-review`); `blocked` opens an issue (label `upstream-blocked`) with the report and the conflicted merges and writes nothing; scheduled runs skip that version while the issue is open. Manual runs take a version, `dry_run` (report only) and `force`.
- `.github/workflows/upstream-playwright-cli.yml` runs weekly with the same verdicts for `microsoft/playwright-cli` (`npm run watch:playwright-cli`, `--apply` to take a clean merge).
- Both workflows need Issues enabled on the repository (a fork has them off by default) for the `blocked` verdict to land anywhere; without them the lookup only warns, but a blocked roll fails the job with the report in the summary and the artifact.
- The automatic merge uses the workflow token: keep the repository setting "Allow GitHub Actions to create and approve pull requests" on, and do not require reviews from branch protection for `roll_*` branches, or the merge step only leaves a comment and the PR waits.

## Start of a session

`node scripts/session-check.mjs` prints nothing when the checkout is coherent and one line per problem otherwise (pin vs installed vs `versions.json`, a stale `lib/cli.js`, once per new version a newer `patchright-core` on npm; the registry lookup runs at most once a day with a 3 s budget). `.claude/settings.json` wires it as a `SessionStart` hook, so it costs no context unless it has something to say; `npm run session-check` prints the status on demand.

## Pitfalls

- Features that only exist in newer playwright-core (e.g. `recording-start`, `install --global`) must be ported by hand once patchright catches up; the roll only merges what upstream changed in the files we fork.
- Never edit `node_modules/patchright-core`; if a daemon behavior must change, it goes through config, flags or a client-side rewrite.
- Windows console flash at `close`: patchright-core 1.62.3's `launchProcess` kill path runs `spawnSync('taskkill ...', { shell: true })` without `windowsHide`; playwright-core 1.63.0 added `windowsHide: true` there. After a roll, `grep -n "taskkill" node_modules/patchright-core/lib/coreBundle.js` and, once the flag is present, drop the "What does flash" paragraph from `skills/patchright-cli/references/platforms.md`.
- `npm run check` fails until the snapshot, the generated help, `versions.json`, `vendor/` and the installed version agree.
